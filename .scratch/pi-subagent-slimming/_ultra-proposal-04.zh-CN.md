# Ultra 提案摘要 — 工单 04

## 推荐方向

使跨进程边界的运行记录（Transcript）成为持久的事证来源，使运行协调器成为完成状态的唯一判定权威，并使每个运行窗口（Run Window）成为独立的、可丢弃的读取器进程。

## 边界

- 在 `collectOutput` 处、即在可能有损的语义解析之前，捕获精确的 stdout/stderr 字节块。`parse.ts` 仅保留为结果/进度层。
- 每个运行（Run）存储一个仅限当前用户访问的存储包：仅追加的版本化 JSONL 日志、原子发现清单和执行租约。`registry.json` v1 保持不变；`tasks.json` 保持不动。
- 日志记录在各通道之间具有连续的序号。启动元数据在最前；由包装器（wrapper）撰写的终止记录在最后。stdout/stderr 字节以 Base64 编码，从而使无效 UTF-8 和被拆分的码点仍可逆还原。
- 对精确序列化后的终止记录之前的日志字节做哈希，而不是仅对解码后的负载字符串做哈希。
- 协调器在子进程退出、两个管道均达到 EOF 以及写入器排空之后，写入并持久校验终止事证。Pi 的 `agent_end`/`agent_settled` 是语义层面的交叉校验，而非操作系统捕获层面的权威。
- 捕获失败是不可逆的不完整，但绝不能阻止 Pi 运行。信号终止、spawn 失败、被遗弃、完整性缺失或管道未排空均属不完整，且不予通知。
- 正常的非零退出可以是一次被完整捕获的失败完成，并通知一次。退出码为零但预期的 Pi 结算（settlement）未发生，则视为协议错误完成，而非成功。

## 格式化器与查看器

- 一个确定性的增量格式化器位于运行记录读取器与 GUI 之间。它负责事件标识、增量/信封（delta/envelope）对账、工具/用量去重、部分行更新以及无损回退。
- 每个运行使用一个查看器进程以实现故障隔离。查看器仅接收协议版本、Run ID 和日志路径；它通过单一字节游标进行回放与尾部跟踪，仅将文件通知视为提示，并以轮询作为回退手段。
- 关闭或崩溃查看器对捕获和通知均无影响。已完成的窗口保持打开。宿主重启不会自动重新打开旧窗口；显式重新打开会回放日志。

## 通知

- `pi_status` 和窗口永不发出通知。协调器仅在产生有效的持久终止记录之后，才创建以 `completion:<runId>` 为键的持久发件箱（outbox）条目。
- 崩溃恢复会从终止事证中重建缺失的发件箱条目。重试复用同一标识。
- 严格的恰好一次可见通知要求目标端确认并对该标识进行持久去重。在此得到证实之前，实现不得过度宣称恰好一次投递。

## 保留与兼容性

- 一个独立的运行记录存储服务在启动时、终态化之后以及每 15 分钟执行一次对账与清扫。
- 在七天时删除非活动存储包，随后按最旧优先删除，直至非活动存储不超过 2 GiB。活动存储包被排除在外，绝不删除。
- 在删除前将符合条件的存储包原子地重命名移入 `trash/`；重启后恢复被中断的删除。所有权不明确的存储包会阻止删除。
- 通知去重回执的存放位置独立于运行记录负载的保留策略之外。

## 实施顺序

1. 冻结模式（schema）、完成判定谓词、发件箱契约以及黄金夹具（golden fixtures）。
2. 实现受限存储、精确字节捕获、租约、终止校验与故障测试。
3. 实现纯解码器/格式化器及生产事件夹具。
4. 实现独立的查看器启动/回放/尾部跟踪与故障隔离。
5. 增加重启对账与保留策略。
6. 在正式切换上线之前，验证 v1 注册表兼容性、两工具公共接口、实际的 Pi 0.85.1、通知目标端与回滚方案。

## 剩余的事证关卡

1. 通知目标端的确认与持久去重契约。
2. 是否存在 spawn 之后的 stdin 或携带机密的参数。
3. 宿主崩溃后 Windows 上的子进程所有权行为。
4. 用于精确流式/工具对账的生产事件标识。

完整的输入事证见 `_ultra-brief.md` 与 `_grilling-exploration-04.md`。
